# WritOn API Findings Register

Last updated: 2026-08-29

This is the cumulative, read-only findings register for WritOn's application APIs and bot subsystem. Bot findings are intentionally isolated from the Android-first stabilization backlog. Status remains `Open` until a fix is implemented and verified by an automated test or an explicit production-safe check.

## Verified positive controls

- Production bot tables currently have RLS enabled, zero policies, and no `anon` or `authenticated` table grants. This matches the server-only database design.
- The production `bot_global_settings` row currently does not contain a Gemini API key.
- Most bot SQL uses parameters, and core publish/interact writes use transactions.
- Applauds and follows use uniqueness constraints to avoid duplicate relationship rows.
- Bot activity and delayed-action tables provide a useful starting point for auditing and queue observability.
- The unauthenticated admin overview returns HTTP 401 in production; this does not mitigate the separate public Spark/MCP surfaces.

## Testing gate required before bot enablement

1. Authentication and permission tests for every admin, Spark, and MCP write operation.
2. Rate-limit, quota, payload-size, tool-allowlist, and malformed JSON-RPC tests.
3. Real migrated-Postgres tests for publishing, interactions, counters, notifications, memory, and ledger writes.
4. Multi-worker queue tests for atomic claim, crash recovery, retry exhaustion, and duplicate delivery.
5. Provider tests for timeout, 429, 5xx, invalid JSON, safety rejection, and cost limits.
6. Moderation, provenance, bot labelling, and human-facing notification tests.
7. Production-safe smoke checks must remain read-only; mutating bot endpoints are never probed against live data during an audit.

The implementation sequence, route policy, schema changes, and acceptance tests are specified in [`bot-remediation-handoff.md`](bot-remediation-handoff.md).
